## 3. M2 失败的完整根因链（5 层，逐层剥开）

每一层都是**实测**剥出来的；修一层，失败点就前移一层。**这是本文最重要的部分。**

### 层 1 — 滑行段冲过点火时刻（已修）
`w.t` 冲过 `DEMO.tli.at` 约 25 s（warp=2000 时一帧 33.3 s），`burnTLI` 里
`tof = DEMO.tli.tof − (w.t − DEMO.tli.at)` 就少了这 25 s。
而该几何下**近月点高度对 tof 极陡：24 s ↔ 115 km**（到达接近切向通过）。
证据（`outputs/route08/diag-m2-aim.txt`）：

| 路径 | 结果 |
|---|---|
| ① 规划路径（`integrateSim` 滑到 t_ign） | ✔ peri 115.95 km / 面 0.0093° / v∞ 0.8565 |
| ② 实飞路径（`advance(1/60)`×warp2000，无 `_advanceStopAt`） | ✘ `no-converge`，periAlt **1.05 km**（撞月） |
| ②b 实飞 + `_advanceStopAt = t_ign` | ✔ 过冲 **0.000000 s** → peri 117.83 / 面 0.0302° |
| ④ 规划态但 tof 少 24 s | ✘ periAlt **1.04 km**（与 ② 一致） |

**修法**：`solveTLI` 设 `w._advanceStopAt = DEMO.tli.at`。

### 层 2 — `burnTLI` 还在用 `startFiniteManeuver`（已修）
`startFiniteManeuver` 是"固定惯性方向 + 速度关机"，`tools/test_lunar_arrival.js` T10 实测把
真近月点打到 **2628 km**。**修法**：换成 `startLunarTransfer`（两阶段有限弧打靶）。

### 层 3 — 阶段 A 只试 1 个种子，残差收不下去（已修）
`startLunarTransfer` 的阶段 A 原来 `tries = min(1, …)`，实测只把位置残差收到 **214.48 km**
（`metA` 要 <60 km），阶段 B 继承这个坏种子后停在 **periErr = +21.33 km**（刚好越过 20 km 验收线），
而 `corrEq` 只用了 15.72/20 m/s ⇒ **是搜索没收敛，不是预算被打满**。
预算扫描（`tools/diag_tli_budget.js`，同一状态同一 aim）：

| 组合 | 阶段A残差 | 结果 |
|---|---|---|
| 默认（tries=1） | 214 km | ✘ periErr +21.33 |
| **A: tries 3 / evals 150** | **57 km** | ✔ peri 119.65 / 面 0.0055° / corrEq 9.49 |
| B: 只加 B 预算 400/150 | 214 km | ✔ peri 115.37 / 面 0.0025° / corrEq 15.79 |
| **C: A+B 都加** | **57 km** | ✔ peri **115.46** / 面 **0.0028°** / corrEq 9.51 |

**修法**：默认值取组合 C。

> ⚠ **同时被推翻的一个建议**：上一轮交接文档建议"`burnTLI` 复用 `solveTLI` 的 `pick.aim`，不要重解"。
> 实测**恰好相反**：用规划态 aim 时所有预算组合全部失败（peri 517~581 km），
> 用实飞态 aim 才成功。原因：`startLunarTransfer` 用 `aim.v1` 构造参考弧，
> 而规划态与实飞态差 2.81 km / 3.33 m/s，在这个敏感几何下足以让参考弧跑偏。
> **必须在真实状态上重解 aim。**

### 层 4 — 点火步长与打靶步长不同源（已修）
即使打靶收敛到 peri 115.46 km，实飞到达近月点仍是 **1 km（撞月）**。
原因：打靶用 `finiteBurnArc` 的步长表，实飞却由逐帧 `advance(1/60)` 驱动 ——
`advance` 会在每个 warp 块的边界把步长夹到 `remain`，步长序列与打靶不同源，
RK4 截断误差不同 ⇒ 关机速度差几 m/s ⇒ 到达近月点差上百 km
（`test_finite_tli.js` C3 用 `advanceBurnToEnd` 时 |Δr| = **0.0000 km**，证明这条链是通的）。
**修法**：`burnTLI` 里用 `w.advanceBurnToEnd(c)` 驱动点火；并把 `advanceBurnToEnd`
改成临时 `warp = 1`（原来隐含假设 warp=1）。

### 层 5 — 面约束的参考时刻错了 4 h（已修）
修完层 4，近月点进了 111±20，失败点变成 **"到达轨道面差 0.15° > 0.1°"**。
原因：`lunarAimPoint` 把站点方向**钉死在设计到达时刻 `tArr`**，但真实近月点比 `tArr`
**早 4.08 h**（`tools/diag_tli_dv.js` 实测 `t − tArr = −14700 s`）。月球 4 h 自转 2.2°，
于是到达那一刻站点已经转走，真实到达面上的面差偏到 0.15°。
- ❌ 试过"残差里改用 `ca.t` 处的站点方向"：残差对 v1 变成非光滑（`ca.t` 自己也随 v1 动），
  LM 直接 `no-converge`（实测 M2 又回到 TLI 瞄准失败）。
- ✅ **修法**：保持钉死，在 `lunarAimPoint` 加外循环，把 `tof` 调成 `aerr.t − this.t` 重解
  （最多 2 次），让设计时刻与到达时刻自洽。

### 3.7 TLI Δv 之谜（已解开）

文档 §1 说 TLI 应约 3050 m/s，实测四个数字不一致。现在四个都解释清楚了：

| 数字 | 含义 |
|---|---|
| **3204 m/s** | `solveTLI` 粗扫的两体兰伯特，从**停车态**出发瞄月心（只用于打分，无面约束、两体漂移） |
| **3391 m/s** | 同上但用**真实状态**出发（把全模型漂移算进去） |
| **3681 m/s** | `lunarAimPoint` 的解 = 3391 + **约 290 m/s 的到达面约束代价**（到达面必须含着陆点方向） |
| **3050 m/s** | 真实 Apollo 11 的值 —— 它的发射窗口本来就是按"到达面天然含着陆点"选的 |

`tools/diag_tli_dv.js` 实测：`|v1| = 10.9369 km/s`、逃逸速度 11.0229 km/s、
**C3 = −1.888 km²/s²**（地心椭圆）、Δv 方向与点火前速度夹角 **11.907°**、
远地点约 415,685 km > 384,400 km ⇒ **物理自洽，能到月球**（真近月点在 95.92 h）。

**结论**：`save_replay.js` 的 TLI Δv 闸门（3.05 ± 0.05 km/s）**当前设计下不可能满足**。
这不是 bug，是设计选择：`07 buildScenario('parking')` 按"停车轨道面与月球轨道面夹角最小"
选 RAAN，而真正该优化的是"**到达面含着陆点**"。若要满足 3.05 km/s，
应把 `solveTLI` 的打分从"两体兰伯特 Δv"改成"全模型 `lunarAimPoint` 的 `aim.dv`"
（后者已经把面约束算进去了），让它去挑一个面约束代价最小的窗口。

## 4. 剩余工作

### 4.1 M5 生成（**已定位到根因：本模型不可行**）

M5 脚本链最长：`sAscent → sTLI → sPlaneSetup → sCircularize → sUndockOnly → sTakeLM →
sLanding → sEVA → sAscentFromMoon → sReturn`。M5 与 M2 的唯一区别是 **M5 走真实上升段**
（`prelaunch`），而 M2 从**构造好的停泊轨道**起步（`startState:'parking'`）。

现状：`"$N" tools/validate_route08.js . M5` → **`gateExit 2`**，停泊轨道三项闸门全过，
但生成期在 `sTLI` 报错、中止：
```
TLI：S-IVB 推进剂不足 —— 剩余 51.55 t（全堆质量 118.0 t），
     最省的两条两体转移窗口也要 Δv 3156 m/s，而剩余推进剂最多只能给 2388 m/s
```

#### 4.1.1 为什么 M2 能过、M5 不能

M2 起步就带着**满油 S-IVB（106.4 t）**，而 M5 必须先做真实上升 + 入轨，
**入轨就烧掉 ~55 t**，到 TLI 只剩 51.55 t。

| | M2（构造停泊轨道） | M5（真实上升） |
|---|---|---|
| TLI 时 S-IVB | 106.4 t | **51.55 t** |
| 可用 Δv 上限 | ~3.9 km/s | **2388 m/s** |
| 该窗口需要的 Δv | 3681 m/s（够） | **≥3259 m/s（不够）** |

#### 4.1.2 根因（三层，逐层实测）

**层 A — 入轨烧掉 55 t，其中约 24 t 是"很低效地圆化"烧掉的。**
`tools/probe_insert_elem.js` 实测（T=12）：S-IVB 点火在 T+551、速度 6.99 km/s，
关机 T+780。关键在 **T+682 之后**：切向速度已经等于圆速度（7793.42 m/s），
只剩残差的**位置项** `(r−rt)/INS_T` 在慢慢收敛，而这段时间：
```
T+682 → T+780（98 s）烧掉 23.6 t 推进剂（≈757 m/s），
          半长轴只从 183.99 km 抬到 184.51 km（≈0.3 m/s 有效 Δv）
⇒ 约 99.96% 的冲量被浪费
```
**为什么**：`vgoResidual` 的位置项用的是**瞬时半径 r**，而 r 在椭圆轨道上每圈只穿过
目标半径 rt 两次 —— 关机判据要等到那一刻，制导就一直（用径向推力、极低效地）把轨道
往 rt 抬。缩小积分步长没用（`INS_H` 0.05→0.002 只把关机从 T+780 挪到 T+783），
说明这不是步长抖振，而是**判据本身相位敏感 + 用径向推力圆化**。
- 想提前关机省油？`T=8` 能把关机挪到 T+677、剩 76.2 t，**但轨道不合格**：
  T+630 时弹道还是负半长轴（亚轨道），T+664 才刚变椭圆，关机时 a≈140 km、e≈6.9e-3
  ⇒ **95 × 184.6 km，过不了停泊轨道闸门**。所以不能靠提前关机省油。

**层 B — 本模型的 TLI 天生比真实贵 ~210 m/s。**
从 185 km 停泊轨道出发，本模型窗口的**脉冲 Δv ≈ 3260 m/s**
（`sqrt(2μ/r+v∞²) − v_circ`，v∞ 影响极小），而真实 Apollo 11 约 3050 m/s。
两体兰伯特的最低分也是 ~3149 m/s。这个差距来自本模型的几何/历元（月距、面约束），
不是搜索算法问题。

**层 C — 到达面约束再加 ~100 m/s。**
`lunarAimPoint` 要求"到达轨道面含着陆点"，实测把窗口 Δv 从两体的 3151 抬到 3259
（+108 m/s，≈0.65° 的面修正）。§3.7 已记录 M2 上这个代价约 +290 m/s。

#### 4.1.3 已经做过的尝试（都实测过，都救不回来）

| 尝试 | 结果 |
|---|---|
| 细相位回退（1/200 圈、滑行 0~3 h、取最省） | ✅ 把最省窗口从 **3473 → 3259 m/s**（tof 100 h / 滑行 156.5 min / v∞ 0.854 / 近月点 115 km）；但仍 > 2388 |
| 放宽 tof 到 104/108/112 h | ❌ 更贵（3293~3306），且合格窗口更少 |
| 加细相位（6 h 范围、60 个候选） | ❌ 最小值仍是 3259，没有更省的合格窗口 |
| 入轨提前关机（T=8 → 76.2 t） | ❌ 轨道不合格（见层 A） |
| 入轨按"最早合格轨道"关机（≈T+708，68.9 t） | ⚠ 只能把 dvMax 抬到 ~2957，仍差 ~300 m/s |
| 理想入轨（理论最省 ≈30.7 t） | ❌ dvMax 上限也只 ~3254，仍差 ~5~80 m/s（取决于相位） |

**结论**：M5 的缺口在 **80~870 m/s** 之间（取决于入轨相位），**任何入轨整定都补不上**，

### 4.5 真实推进剂（**预算分析表明 18410 kg 不够**）

`CSM.propMass: 24000 → 18410`、`LM.ascentProp: 3000 → 2353`。

**但先看这笔账**（M2 实测，`SM` 用掉 12473 kg）：
```
M2 实测 SPS 消耗：12473 kg（LOI-1 + LOI-2 + MCC）
真实 Apollo 11 预算：LOI-1 11378 + LOI-2 646 = 12024 kg，全任务总预算 18410 kg（含 TEI 6245）
若油箱只有 18410：18410 − 12473 = 5937 kg 留给 TEI，而 TEI 需要约 6245 kg
                  ⇒ 差约 308 kg
```
另外 M2 实测 LOI-1 Δv = **819 m/s / 404 s**（文档写 ~889 m/s / 357.5 s）。
⚠ 文档自身有内部矛盾：按能量算 `v∞ = 0.87 → LOI-1 ≈ 787 m/s`，要 889 m/s 得 `v∞ ≈ 1.1`。
**现有测试用"解析能量一致的 Δv"判据，不要为了让 889 成立去放宽 v∞ 区间。**

所以改到 18410 之后**大概率会在 TEI 阶段报 `noPropellant`**。这时**不许靠补油绕过**，
要么缩短 LOI 点火时间（降重力损耗）、要么如实报告该模型做不到真实燃料预算。
注意：**M3 只耗 14 kg**（场景初态已经接近目标），所以 **M3 通过 ≠ 真实燃料够**。

## 5. 验收盲区（**务必知道，别误判"通过"**）

1. **M3 的闸门是空的。** `save_replay.js` 对 M3 **不生成任何 gate**：
   停泊/TLI 只对 `['M1','M2','M5']`，着陆/溅落只对 `M4/M5`。
   所以 M3 的"生成通过"只等价于"没有 `生成模式：` 日志"。
   M3 真正的断言（150 m / 1 m/s / 300 s 保持）必须人工核对 `M3-run.json` 的 `rndz` 字段。
2. **TLI Δv 闸门实际上从不触发。** 闸门正则是 `/Δv\s*=\s*([\d.]+)\s*km\/s/` 且日志须匹配
   `/TLI 点火完成|TLI burn complete|TLI.*Δv/`。本轮已给 `burnTLI` 加了一条
   `TLI 点火完成：… Δv(弦长) 3314 m/s` —— 仍然匹配不上（要 `Δv = X km/s`）。
   也就是说 TLI Δv 偏到 3.68 km/s 也不会被拦（详见 §3.7）。
3. **`lunarAimPoint` 对 tof 极度敏感**（24 s ↔ 115 km）。所有调用点都必须保证在**精确的** `t`
   上求解，任何"多走/少走几帧"都会崩。
4. **`lunarAimPoint` 现在最多递归 3 次**（`opts._aimIter`），单次求解 40~60 s。
   `solveTLI` 最多试 3 个候选 ⇒ 生成时可能花几分钟。这是**离线生成**，可接受，但要知道。
5. `validate_route08.js` 的 gate 目录只拷贝 `00~03` 四个 js，所以 `save_replay.js` 用的物理模块
   与浏览器里跑的**必须同版本**；改了 `00~03` 后要重跑。
6. `apollo11/webdata/traj/` 现有 `M1/M2/M3/M4.json`，**已在本轮更新为验证通过的新产物**；
   `M5.json` 尚不存在（M5 未生成）。旧文件（17:36/17:44）是上一轮的演示值，已被覆盖。
7. **M5 不是"还没调好"，是"本模型做不到"**：缺口 80~870 m/s，瓶颈在上升段（见 §4.1）。
   别把时间花在 TLI 搜索/入轨整定上 —— 那两处已经扫到边界了。
8. `tools/probe_parking.js` 的关机检测会**把抖振中的瞬时收油误判成关机**，
   它的"轨道"一列不可信；看轨道请用 `tools/probe_insert_elem.js`。
9. `solveTLI` 的第二遍（细相位回退）**只在第一遍失败/买不起时运行**，
   单次最多 24 次 `lunarAimPoint`（每次 40~60 s），所以 M5 生成会比以前慢几分钟；
   这是**离线生成**，可接受。
